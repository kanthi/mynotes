# Message Ordering

Once you run multiple consumers, retries, or multiple topics, messages will inevitably arrive **out of order**. A `TicketCanceled` event can reach a read model before `TicketBookingConfirmed`, or two updates to the same entity can race. Reliable event-driven systems handle ordering explicitly rather than assuming FIFO delivery.

## Learning & Build Goals

- **Learn:** Why message ordering breaks in distributed systems; strategies to prevent races and state conflicts; partitioning by entity key and optimistic entity versioning.
- **Build:** Refactor the ticket aggregator to preserve or tolerate ordering using partitioning and versioning; handle out-of-order events safely without corrupting state.

## Why Messages Arrive Out of Order

1. **Multiple consumer replicas:** Consumer A processes event 1 slowly while Consumer B finishes event 2 first.
2. **Retries:** Event 1 fails transiently and is retried 5 seconds later, after event 2 already succeeded.
3. **Separate topics:** Events published to `events.BookingMade` and `events.TicketConfirmed` are consumed by independent subscriptions with independent lag.

## Ordering Strategies

| Strategy | How It Works | Trade-offs |
|----------|--------------|------------|
| **Broker Partitioning** | Hash by `entity_id` (e.g., `booking_id`) so all events for one entity land in the same Kafka partition and single consumer | Preserves per-entity order on one topic; does **not** order across different topics; hot keys can skew load |
| **Entity Versioning** | Attach monotonically increasing `version` (or timestamp) to each event; ignore or defer stale versions | Works across retries and brokers; requires version tracking on producer and consumer |
| **Commutative / Upsert State** | Merge partial fields independently (`confirmed = true`, `refunded = true`) instead of overwriting full structs | Simplest when applicable; naturally tolerates out-of-order arrival |
| **Nack & Retry on Missing Prerequisite** | If `TicketConfirmed` arrives before `BookingMade`, return an error so the broker retries after a short delay | Works for brief cross-topic lag; requires bounded retries + poison queue |

## Optimistic Entity Versioning in SQL

```go
package ordering

import (
	"context"
	"database/sql"
	"fmt"
)

// ApplyVersionedUpdate updates the projection only if the incoming event is newer.
func ApplyVersionedUpdate(
	ctx context.Context,
	db *sql.DB,
	ticketID string,
	status string,
	eventVersion int64,
) (applied bool, err error) {
	const query = `
		INSERT INTO ticket_views (ticket_id, status, version)
		VALUES ($1, $2, $3)
		ON CONFLICT (ticket_id) DO UPDATE
		SET status = EXCLUDED.status,
		    version = EXCLUDED.version
		WHERE ticket_views.version < EXCLUDED.version
	`
	res, err := db.ExecContext(ctx, query, ticketID, status, eventVersion)
	if err != nil {
		return false, fmt.Errorf("apply versioned update: %w", err)
	}
	n, err := res.RowsAffected()
	return n > 0, err
}
```

When an older redelivered event (`version = 2`) arrives after `version = 3` was already applied, `WHERE ticket_views.version < EXCLUDED.version` evaluates to false, leaving the newer state intact and letting the handler safely `Ack`.

## Common Pitfalls

- **Relying on wall-clock timestamps for ordering:** Clocks across servers drift. Use a monotonically increasing sequence number generated by the entity's database row or stream offset.
- **Global single-partition ordering:** Forcing all events into one partition serializes the entire system to one consumer and destroys horizontal scalability. Partition by aggregate/entity ID instead.
