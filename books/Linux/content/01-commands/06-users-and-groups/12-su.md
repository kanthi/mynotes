# su

## Overview

`su` ("substitute user") starts a shell or runs a single command as another user account. On modern Linux systems, **`sudo`** is preferred for policy-controlled privilege elevation and audit trails, while `su` remains essential for switching to service accounts, rescue environments without `sudo`, and legacy scripts. For root-to-user switches in scripts, `runuser` is a lighter non-PAM-prompting alternative.

## Syntax

```bash
su [options] [-] [user [argument...]]
su [options] -c "command" [user]
```

## Common Options

| Option | Description |
|--------|-------------|
| `-`, `-l`, `--login` | Start a full **login shell** (resets `HOME`, `USER`, `PATH`, and loads target's profile) |
| `-c CMD` | Run a single command as the target user and exit |
| `-s SHELL` | Override the target user's login shell (useful for service accounts with `/sbin/nologin`) |
| `-w LIST` / `--whitelist-environment` | Preserve only specific environment variables across `su -` |
| `-p`, `-m`, `--preserve-environment` | Keep the caller's environment (use carefully—can leak `HOME` or `PATH`) |

## Key Use Cases

1. Open a clean login shell as `root` on systems configured with a root password (`su -`)
2. Switch into a service account (`postgres`, `www-data`) for maintenance (`sudo su -s /bin/bash www-data`)
3. Run a single command as another user in rescue mode (`su -c 'systemctl status ssh' root`)

## Safety

- Always use `su -` (with the dash) when switching users interactively; plain `su` keeps your old `PATH` and `HOME`, which can accidentally write root-owned dotfiles into your personal home directory.
- From an unprivileged account, `su` asks for the **target user's** password (not your own `sudo` password).
- Avoid `su -c` with unquoted variables—quoting mistakes run as the target user.

## Examples with Explanations

### Open a clean root login shell

```bash
su -
```

Prompts for the `root` password and resets `HOME=/root` and `PATH`.

### Run a single command as root

```bash
su -c 'systemctl status ssh' root
```

### Switch to a service account (including accounts with `nologin`)

```bash
sudo -u postgres -i                  # preferred when sudo is available
sudo su -s /bin/bash www-data        # useful when www-data has /usr/sbin/nologin
```

### Preserve only specific environment variables

```bash
su -w LANG,TERM - alice
```

### Non-setuid script alternative when already root (`runuser`)

```bash
sudo runuser -u postgres -- pg_isready
```

`runuser` avoids `su`'s setuid/PAM overhead when invoked by `root` in automated scripts.

## Notes & Pitfalls

- On Ubuntu (especially Server and cloud images), the `root` account is locked with no password by default, so `su -` fails—use `sudo -i` instead.
- Chaining `sudo su -` works but obscures per-command audit logs compared to `sudo -i` or `sudo -u user cmd`.
- `su` does **not** set up a full `systemd-logind` session (`XDG_RUNTIME_DIR`), so `systemctl --user` will fail with a D-Bus error inside `su`—use `machinectl shell user@` or `ssh user@localhost` for user-level systemd work.

## Related Commands

- `sudo` — policy-based, audited privilege elevation
- `runuser` — run commands as another user from `root` in scripts
- `loginctl` / `machinectl` — clean `systemd-logind` user sessions
- `whoami` / `id` — verify current effective user and groups
